# AI-Assisted Code Review

## Purpose

This document provides guidance for code review when AI assistance is involved — either in producing the artifact under review, or in supporting the review activity itself. It complements `docs/code-review-best-practices.md`.

Within SECAV-O, a `secav:CodeReview` of an AI-assisted artifact is also a `secav:HumanValidationActivity`. The original `secav:CodeImplementation` activity is linked to `secav:assistedByAI`; the review must be linked back via `secav:requiresHumanValidation` to preserve traceability.

---

## 1. Context: how AI changes code review

AI coding assistance increases both the volume and the size of code submitted for review.

- AI-assisted pull requests are approximately **2.6× larger** than non-assisted ones (LinearB benchmark via CodeRabbit [1]).
- In teams that adopted AI coding tools, **review time increased 91%** and **PR size increased 154%** (Faros AI data via Saigon Technology [7]).
- AI-generated code typically arrives without the decision history that explains *why* it was written that way.
- Code generated by AI can compile and pass basic tests while failing under load, edge cases, or invalid inputs [1].

These effects mean that review practices designed for human-only code may produce worse outcomes when applied unchanged to AI-assisted code.

---

## 2. Core principle: AI assists, humans are responsible

The review objective is **human review assisted by AI**, not AI review replacing humans.

| AI is effective at | AI is weak at |
|---|---|
| First-pass review of common patterns | Business logic correctness |
| Style and consistency across large codebases | Subtle race conditions |
| Flagging known anti-patterns | Understanding product intent |
| Repetitive or templated checks | Mentoring and knowledge transfer |

AI review is advisory. It must not approve or block a change autonomously, and must not be used to trigger automatic merges [11][13].

## 3. Recommended practices

### 3.1 Review intent before the diff

Before reading lines of code, verify that the change does what the team agreed to build — not just that it "looks correct" [2]. Keep an auditable trail linking the change to its intent (ticket, specification, or prompt). This prevents scope drift and misalignment, which are more common with AI-generated code [6].

### 3.2 Keep changes small

Large diffs overload reviewer working memory and degrade outcomes [1]. Request scoped changes from the AI and split large PRs before submitting for review.

### 3.3 Layered pipeline: deterministic tools first, then AI, then human

A recommended review flow:

```
Author opens PR
  → Linters, type checkers, secret scanners, static security analysis
  → AI first-pass review (configured with project conventions)
  → Human review (mandatory for production paths and sensitive code)
  → CI with tests and integration checks
```

AI tools should surface common problems before humans invest review time [11]. Static analysis combined with LLM review gives better security signal than either alone [12].

Automated security scanning is no longer optional for AI-assisted code [6].

### 3.4 Risk-based triage

Not all PRs carry the same risk. Classify before routing:

| Risk level | Signals | Review approach |
|---|---|---|
| Routine | Format, documentation, low-complexity logic | AI review may be sufficient for flagging |
| Attention | Changed business logic, new dependencies | AI first pass + full human review |
| Security-critical | Auth, data access, cryptography, PII paths | Human review required; AI review is supplementary |

Any change that appears security-sensitive must trigger human review [10]. Monitor false negatives: high-risk PRs incorrectly cleared at a lower tier [10].

### 3.5 Provide context and configure the tool

Most AI review tools accept project-specific rules, conventions, and focus areas [3][4]. If false positives are high, adjust configuration or add more context rather than disabling the tool. Reusable security checklists (SQL injection, XSS, missing authentication, secrets in code) improve consistency [13].

Instruct the AI tool to explicitly mark what **requires human judgment** [13].

Google's AutoCommenter study found that AI-assisted review went beyond traditional static analysis for 66% of evaluated best-practice violations [5].

### 3.6 Manage false positives and alert fatigue

False positives erode trust quickly and cause reviewers to ignore even legitimate alerts [7][9]. Actions to take:

- Tune sensitivity thresholds based on observed false positive rate.
e- Tag AI suggestions as: **accepted**, **dismissed**, or **false positive**. Teams using this practice report action
 rates above 30%.
- Note that AI review comments are adopted only 1–19% of the time on average; quality of suggestions matters more than quantity.
- Measure the impact of tuning on PR cycle time and escaped defects [7].

### 3.7 Integrate into existing workflow

Integrate AI review into the PR platform the team already uses (GitHub, GitLab, Bitbucket). Run it asynchronously so model latency does not block CI [4][13].

### 3.8 Data privacy and security

Sending code to a hosted LLM may expose sensitive information: API keys, proprietary algorithms, PII, business logic. Before adopting an AI review tool:

- Avoid public APIs without a data processing agreement.
- Prefer auditable, self-hosted, or enterprise-contracted models where possible.
- Establish governance over model changes and data retention policies [12].

### 3.9 Measure and improve

Recommended metrics for AI-assisted review:

| Metric | What it indicates |
|---|---|
| False positive rate (dismissed suggestions) | Tool calibration quality |
| Security bug detection improvement vs. baseline | Value of AI pass |
| PR cycle time | Whether AI speeds or slows review |
| Defects escaped to production | Review effectiveness overall |

Review false positives periodically and retune [11].

## 4. Common errors to avoid

- **Approving because the AI approved.** AI approval does not mean production-ready.
- **Reducing human review because "the AI ran."** This increases false negatives [13].
- **Reviewing large diffs line-by-line without a strategy**, or approving without reading [2].
- **Relying only on diff analysis.** Many tools analyze only changed lines and miss broader context.
- **Ignoring the social dimension of review:** mentoring, shared team knowledge, and design discussion are not AI-replaceable [8].

---

## 5. Quick checklist

- [ ] PR linked to its intent (ticket or specification)
- [ ] PR size limited; large changes split before submission
- [ ] Linters, type checks, secret scan, and security scan run before AI review
- [ ] AI review configured with project-specific rules
- [ ] Human review mandatory for production paths and sensitive code
- [ ] AI suggestions tagged: accepted / dismissed / false positive
- [ ] False positive rate, cycle time, and escaped defects measured
- [ ] Data privacy policy defined for code sent to the model

## 6. SECAV-O integration

| Concept from this document | SECAV-O term |
|---|---|
| AI-assisted coding activity | `secav:AIAssistedActivity` (subclass of `secav:EngineeringActivity`) |
| Link from activity to AI system | `secav:assistedByAI` (ObjectProperty) |
| Human review of AI-assisted code | `secav:HumanValidationActivity` (subclass of `secav:ReviewActivity`) |
| Link from AI activity to validation | `secav:requiresHumanValidation` |
| Review findings as evidence | `secav:ReviewFinding` (subclass of `secav:Evidence`) |
| Review record artifact | `secav:ReviewRecord` (subclass of `secav:Artifact` and `secav:Evidence`) |
| Acceptance criteria applied | `secav:AcceptanceCriterion` |

The AI system used must be recorded as a `secav:AISystem` instance linked via `secav:assistedByAI` from the generating `secav:EngineeringActivity`, not from the artifact or the review record.
